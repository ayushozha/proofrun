# ProofRun

ProofRun turns a supported HackerOne program URL into a narrowly bounded security observation. The primary path accepts [Acronis](https://hackerone.com/acronis), confirms its current program and eligible scope through HackerOne's researcher API, and permits **one inert, read-only search-marker request** to the fixed public search page. It records the HTTP status and checks for the marker only in the first 256 KiB of the response. Reflection alone is not a vulnerability: this path always ends inconclusive and creates no bounty report.

Senso supplies a versioned passage from ProofRun's pinned operating policy; Guild gates the run; AkashML selects the allowed check and explains the observation; ClickHouse stores and queries a normalized row in `proofrun_web_checks`. Missing policy, scope, or sponsor approval stops the request. The UI shows the source, observation, and sponsor trace separately.

Secondary paths are a live, read-only [Vercel](https://hackerone.com/vercel) structured-scope watch; an owned, loopback-only authorization training target; a gated live Vercel project-read check that requires two compliant accounts owned by the researcher; and a source audit of `https://ayushojha.com`. The watch does not probe Vercel. The training target is never reportable.

## Run locally

Node.js 24 or newer is required. In PowerShell:

```powershell
Copy-Item .env.example .env
# Fill .env locally; do not commit it or paste keys into chat.
npm start
```

Open `http://127.0.0.1:8787`. Acronis is the default URL. Select **Review current scope**, inspect the returned asset and program rules, then select **Run one read-only probe**. This live path needs the HackerOne API token and all four sponsor connections; it does not need browser capture, a Vercel account, or a second test identity. The target request is a single `GET` to `https://www.acronis.com/en/search/` with a random alphanumeric `query` marker. The worker sends the researcher's HackerOne alias in User-Agent, refuses redirects, reads at most 256 KiB of the response, and does not retry the target. The result is an observation, not a finding or report.

The optional **Watch Vercel structured scope** panel reads the Vercel program's complete structured scope, stores a ClickHouse baseline, and compares later snapshots. It needs HackerOne API access and the four sponsor connections, but no Vercel test accounts. It does not detect edits to free-text program policy or per-asset instructions, and a scope change does not authorize target testing.

The **AyushOjha.com owned-site audit** takes that exact URL, a private local checkout of its GitHub source configured by `OWNED_SITE_REPO_DIR`, and all four sponsor connections. It also needs `uvx` and a Python 3.12 runtime to launch Semgrep CE. Semgrep checks Payload collection access rules for broad signed-in-user permissions; the worker makes one anonymous `GET /api/access` on the site. ClickHouse stores and queries only normalized rule/path/line metadata; the UI also shows the public response status and collection names. Senso provides the pinned operating policy, Guild gates the check, and AkashML chooses and reviews it. The UI labels the result **source only**: a code match does not establish the deployed revision, intended role policy, or a live unauthorized read/write. No private records or authenticated site paths are accessed, and this path cannot create a HackerOne report. Set `OWNED_SITE_URL=https://ayushojha.com` and an absolute `OWNED_SITE_REPO_DIR` in the ignored `.env`; clone the site repository privately, outside Git tracking. Run `npm run senso:seed` after the updated policy is checked in, set the returned `SENSO_POLICY_CONTENT_ID`, and publish the updated Guild gate before running this path.

For the separate Vercel project-access path, load the [Edge/Chrome capture extension](extension/README.md), visit the Vercel program while signed in, click the extension's **Capture program** button, then return to ProofRun and select **Load and review scope**. The browser capture supplies visible policy text; the HackerOne API confirms structured scope. The **Load the controlled training case** button runs a paired owned training target: an exposed case where a second identity reads the owner's server-held private sentinel, and a protected case where the same read is denied. ProofRun queries ClickHouse for both verdicts. This validates the detector's positive and negative behavior on a controlled target; it does not establish a Vercel or other bounty finding or authorize a live Vercel request.

The `.env.example` file lists every required variable. For Guild, publish and install the narrow [gate agent](guild/README.md) first. Set `AKASHML_MODEL` in `.env`; the application contains no fixed model ID. The ClickHouse URL must be its HTTP endpoint. For a live check, `VERCEL_PROJECT_ID` must belong to the account behind `VERCEL_OWNER_TOKEN`; `VERCEL_OTHER_TOKEN` must belong to a separate account you own that is not a member of the owner's team. Set optional `VERCEL_TEAM_ID` for a team-owned project; ProofRun sends the same team ID in all three control requests.

[Vercel's program policy](https://hackerone.com/vercel?type=team) requires two owned accounts for cross-tenant testing and a visible HackerOne researcher alias on test accounts. Register them with distinct aliases such as `HACKERONE_API_USERNAME+owner@wearehackerone.com` and `HACKERONE_API_USERNAME+other@wearehackerone.com`; [HackerOne supports multiple aliases](https://docs.hackerone.com/en/articles/8404308-hacker-email-alias). Before any live project request, ProofRun checks both Vercel user IDs and emails through `/v2/user` and blocks duplicate identities or non-alias emails. The current `@wasmer.io` owner account is therefore gated from live checks until replaced with a compliant test account.

For Senso, create an API key, set `SENSO_API_KEY` in the ignored `.env`, then run `npm run senso:seed`. The script uploads [ProofRun's operating policy](docs/proofrun-policy.md) to your Senso knowledge base, waits for indexing, and prints its `content_id`. Set that value as `SENSO_POLICY_CONTENT_ID` in `.env` and restart the app. Each run retrieves context scoped to that document and shows the returned version in its sponsor trace. Senso tracks ProofRun's own permitted actions; current HackerOne scope comes from the researcher API. A live Vercel project check additionally needs the signed-in program page. Senso ingestion and retrieval use credits. Until a real key and document are configured, runs stop.

The demo's [ClickHouse Cloud service](https://console.clickhouse.cloud/services/7cec452a-7fa4-419a-82c3-1710d18aca49/console/database/default/table/proofrun_checks) is `proofrun` on the Basic plan in AWS Oregon. Acronis observations use the native `proofrun_web_checks` MergeTree table and a query for the run's normalized verdict. Vercel policy watch uses a separate persistent scope-snapshot table; the project-access path uses `proofrun_checks`. [Recorded lab rows](docs/assets/clickhouse-proofrun.png) predate the live Acronis run and should not be used as evidence of that run. The service idles after 15 minutes and allows the current browser and local-app egress IPs; update its IP access list if the demo moves networks.

## Workflow and limits

Acronis accepts only `https://hackerone.com/acronis`. Before the target request, ProofRun checks that the HackerOne API reports the program open, `*.acronis.com` eligible for submission, and the current policy's alias and rate rules. It sends one unauthenticated public-search GET with an inert marker, refuses redirects, and records only the HTTP status, whether the marker was found in the captured first 256 KiB, and a bounded detail. A target network failure is recorded as no response. No cookies, credentials, exploit payloads, follow-up probes, or report submission are part of this adapter. Search-term reflection is ordinary behavior and **never** establishes impact or a reportable vulnerability by itself.

Policy watch accepts only `https://hackerone.com/vercel`. It reads the program and all structured-scope pages, normalizes asset identifiers and submission/bounty eligibility, and compares the complete snapshot with ClickHouse history. With no previous snapshot, it records a baseline; later runs report exact additions/removals or no change. The displayed alert links to the source and includes the fetch time. The watch does not detect changes to free-text program policy or per-asset instructions. A scope change does not authorize testing or establish a vulnerability.

The separate project-access adapter checks only `GET /v9/projects/{idOrName}`. A live run requires a fresh signed-in browser capture, eligible structured scope from the HackerOne API, all four sponsor services, and two distinct, alias-registered Vercel accounts. It makes one owner request, one other-account request, and an anonymous control only if needed. No Vercel response bodies, access tokens, project IDs, raw HackerOne policy text, or report details leave the local worker. AkashML receives the ProofRun-owned Senso policy passage and normalized observations; Guild and ClickHouse receive normalized run metadata.

A `candidate` is a prompt for investigation, not a confirmed vulnerability. Vercel requires a complete, reproducible impact demonstration and a screenshot or unedited video attached for platform findings. The report editor gives the researcher a draft to check against the raw evidence and revise after independently reproducing the issue. Lab runs cannot be submitted. HackerOne bug-bounty submissions also require approved ID verification; `.env` keeps `HACKERONE_ID_VERIFIED=false` until the researcher confirms that status.

In the training run, the local service creates fresh isolated owner and other credentials plus a private sentinel, then probes its exposed and protected cases with owner, other, and (when needed) anonymous controls. Only normalized observations reach ClickHouse; the run succeeds as a detector validation when ClickHouse returns `candidate` for the exposed case and `expected` for the protected case. The sentinel and credentials remain local. The lab produces no bounty report draft and cannot be submitted.

**API submission is blocked in this prototype.** The documented [direct HackerOne report API](https://api.hackerone.com/hacker-resources/) has no media-attachment field. HackerOne documents media upload for report intents, but that route requires a program to enable Report Assistant; Vercel's signed-in page says to submit without Report Assistant. Copy the reviewed draft into HackerOne and attach the required media there before submitting. ProofRun does not claim to have submitted a report.

## Verification

```powershell
npm run smoke
```

This smoke check exercises Acronis scope validation and the one-request marker behavior, plus the capture, intake, sponsor adapters, exposed and protected owned training cases, separate ClickHouse verdicts, and submission guard against mock service endpoints. It confirms the detector distinguishes a known exposure from its protected control in the local fixture. It does not by itself prove live sponsor access, a third-party vulnerability, HackerOne submission, or bounty eligibility. In one observed live Acronis run, the HackerOne scope check passed, one target GET returned HTTP 200, the response exceeded the 256 KiB cap, the marker was not observed in the captured prefix, and the ClickHouse query took 96 ms. That says nothing about marker presence later in the response; the verdict was inconclusive and no report was produced. No license file is currently checked in.

In the observed owned-site run, the private checkout at commit `bf750744a564` produced 11 Semgrep access-rule candidates; the one anonymous `/api/access` request returned HTTP 200; Senso, Guild, AkashML, Semgrep, and ClickHouse completed; and the ClickHouse query took 122 ms. The result is **source-only**. It does not prove that any deployed account can read or change another user's data. The source checkout is private, so reproducing this scan requires authorized access to that repository.
